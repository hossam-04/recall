# recall — Learning Project

## What this is

A spaced-repetition system for interview prep, built end to end in TypeScript to
learn full-stack web engineering. Cards can be written by hand or generated by
Claude from a subject or from pasted source material — but nothing enters the
bank without me approving it first.

**In scope:** HTTP APIs and request validation, session auth (registration,
login, cookies, CSRF, authorisation), Postgres schema design and hand-written
SQL, a React UI, three layers of tests, and an LLM integration done properly —
structured outputs, token and cost accounting, prompt caching, retries, graceful
degradation, and an eval suite.
**Out of scope:** deployment and hosting, deck sharing between users, rich card
content (images, syntax highlighting), file uploads, mobile layout. Do not
suggest these.

**The FSRS scheduler is a stretch milestone (M6), not part of the plan.** M1
ships SM-2. See ADR-003 for what that cut costs.

## Commands

- Dev: `npm run dev` — api on :3000, vite on :5173
- Test: `npm test`
- Verify (the done condition): `npm run verify`
- Browser e2e: `npx playwright test`
- Evals: `npm run eval` — **calls the real API and costs real money.** Never in
  CI, never in `verify`.
- Inspect schema: `psql recall -c '\d+ cards'`
- Inspect spend: `psql recall -c 'select model, sum(cost_cents) from generations group by 1'`

Setup, once:

```bash
brew install node postgresql@18
brew services start postgresql@18
createdb recall
npx playwright install chromium
```

### The oracle, and its honest limit

This project has a weaker correctness authority than `redis-clone` or
`png-from-scratch`, and that is a real cost of choosing it:

| Authority | Covers | Written by |
|---|---|---|
| Zod + `messages.parse()` | LLM output is well-formed and typed | me (schema), SDK (enforcement) |
| Postgres constraints | invalid state cannot be stored | Postgres |
| `tsc --strict` | type errors across the codebase | TypeScript |
| Playwright + real Chromium | the app works in a real browser | me (tests), Chromium (execution) |
| Eval suite | generation quality does not regress | **me — the weakest rung** |
| `ts-fsrs` differential test | scheduler correctness | someone else — **M6 only** |

Two things here fail silently and must be checked deliberately: prompt caching
(confirm `cache_read_input_tokens > 0` on a repeat generation) and the eval
itself (weaken the prompt on purpose and confirm the score drops — an eval that
never goes down is measuring nothing).

## Learning mode — do not skip

I am a new CS grad. Claude writes the code; I must understand every decision.

- Before writing non-trivial code, state the problem and ask me to predict the
  approach. Wait for my answer.
- Explain every choice as: chose X / rejected Y / would switch if Z.
- Never justify with "this is standard practice." Say why.
- Max ~50 lines per chunk, then stop and check I'm following.
- When a build or test fails, explain what the error actually means before
  fixing it.
- If I'm stuck, give escalating hints (nudge → narrow it down → answer).
  Do not jump to the answer.
- Roughly weekly, inject a realistic bug and make me find it.
- End each session: ask me to explain back what we built, then probe weak spots.

## Guardrails

- No library may do the interesting part for me. Parsing, concurrency,
  eviction, and persistence are hand-rolled — that is the entire point.
- Prefer the standard library. Any new dependency needs a one-line
  justification and my approval.
- Write tests as we go. Show me the failing test before the fix.

### Applied to this project

The hand-rolled list here is: the SM-2 scheduler, session auth (issue, verify,
revoke), CSRF, every SQL query, the migration runner, the generation prompt, and
the eval harness. Libraries do the parts that are dangerous to hand-roll or that
are not the lesson: `argon2` for password hashing, `zod` for schema
declaration, `pg` for the wire protocol, `@anthropic-ai/sdk` for the API client,
React for rendering.

**Specifically banned:** Next.js, Prisma, Drizzle, and any auth library
(better-auth, Auth.js, Lucia). Each one would do the exact thing this project
exists to teach. See ADR-001.

**No code is copied from `redis-clone` or `png-from-scratch`.** Where concepts
overlap — request framing, validating untrusted input, buffering — I re-derive
them in TypeScript.
